## P2-02 Settings and environment
- **Fixed in code, not env:** JWT algorithm HS256, issuer, audience, cookie names, TOTP parameters, API prefix `v1`. A deployment must not be able to weaken them; tests assert an env `JWT_ALGORITHM=none` is ignored. HS256 because one service signs and verifies, so there is no key distribution problem; the signing key is separate from `DJANGO_SECRET_KEY` and ≥ 50 chars in prod (spec value; Phase 1 had 32).
- **Refresh lifetime default 24 h (`JWT_REFRESH_LIFETIME_SECONDS`, bounds 1 h–30 d).** Tokens rotate on every use, so this is an *idle* timeout: a dashboard unused for a day re-authenticates with password + MFA. Rejected: 7–30 days (long theft window; reuse detection only fires if the thief and the user both use the token). No absolute session cap in Phase 2 (see OPEN-QUESTIONS).
- **SameSite=Lax (`COOKIE_SAMESITE` input).** Lax keeps top-level navigation working and still blocks cross-site POST/XHR cookies; Strict would drop the session on every inbound link. Requirement this creates: dashboard and API must be **same-site** (same registrable domain, e.g. `dashboard.x.com` and `api.x.com`). `SameSite=None` is refused by settings. If the dashboard lands on a different registrable domain, this decision must be revisited together with CSRF.
- **Cookie names:** `__Host-access` and `__Host-csrftoken` (Secure, Path=/, no Domain); refresh is `__Secure-refresh` because it is path-scoped to `/v1/auth/`, which `__Host-` forbids. Setting `AUTH_COOKIE_DOMAIN` downgrades access/CSRF to `__Secure-`. Dev (plain HTTP) uses unprefixed names because browsers reject prefixed cookies without Secure.
- **CSRF cookie is not HttpOnly** (double-submit: the SPA must read it). The auth cookies are HttpOnly.
- **Credentialed CORS** (`CORS_ALLOW_CREDENTIALS=True`) is always on in settings but prod refuses to start unless `CORS_ALLOWED_ORIGINS` is a non-empty explicit list of `https://` origins (also applied to `CSRF_TRUSTED_ORIGINS`). `as_origins` rejects wildcards, paths, trailing slashes and non-http(s) schemes.
- **`TRUSTED_PROXY_COUNT`, `AXES_FAILURE_LIMIT`, `LOGIN_RATE_LIMIT_PER_MINUTE` have no prod default.** Wrong values here either disable lockout/rate limiting or let a client forge its address. `LOGIN_RATE_LIMIT_PER_MINUTE` was optional in Phase 1; this is a deliberate tightening (deployment impact listed in ENV-VARIABLES-DELTA.md).
- **TOTP SHA-1 / 6 digits / 30 s / ±1 step.** Google Authenticator and most apps ignore the `algorithm` URI parameter and always use SHA-1; choosing SHA-256 would silently break enrolment for those apps. RFC 6238 permits SHA-1; the secret is 160 bits and replay is blocked (P2-07).
- **`MFA_REQUIRED_ROLES`** is validated against the known role names (a typo such as "Campaign Manger" would silently exempt a role) and prod requires both Admin and Campaign Manager. Role names live in `apps/accounts/roles.py` (pure constants) so settings and later code share one source.
- **Axes settings are defined here; `axes` is installed and wired in P2-10** (it adds migrations and a middleware/backend, which belong with the lockout tests). `AXES_LOCKOUT_PARAMETERS=[["username","ip_address"]]` locks one account from one address only; the axes semantics are re-verified against the installed version in P2-10.
- **Phase 1 files touched by this task (necessary consequences, no behaviour removed):** `docs/phase-1/ENV-VARIABLES.md` (the drift test reads it, and P2-02 explicitly asks for it), `tests/conftest.py` and `tests/config/test_settings.py` (new required prod variables, JWT key length), `scripts/gen_throwaway_env.py` (CI deploy check needs the new variables).

## P2-03 User model extension
- **Fields (additive migration `0002_user_epoch_and_profile`):** `full_name`, `auth_epoch`, `password_changed_at`. `first_name`/`last_name` from `AbstractUser` stay (dropping them would not be additive) and are unused. Email remains the identity (case-insensitive unique from Phase 1).
- **`db_default` as well as `default`.** Django's plain `default` drops the column default after `ADD COLUMN`, which would make an older app version inserting a user during a rolling deploy fail on NOT NULL. With `db_default` the SQL keeps `DEFAULT 0` / `DEFAULT ''` (checked with `sqlmigrate`); a test inserts a row the way old code would. The migration reverses cleanly (`sqlmigrate --backwards`).
- **Epoch is monotonic by construction.** Only `bump_auth_epoch()` changes it, as an atomic `UPDATE … SET auth_epoch = auth_epoch + 1`. `save()` never writes the column (it passes an explicit `update_fields` without it) and `update_fields=["auth_epoch"]` raises. Rejected: `self.auth_epoch += 1; save()`, because a stale in-memory copy would overwrite a higher value and revive revoked tokens. The column has a DB `CHECK (auth_epoch >= 0)` from `PositiveIntegerField`.
- **Password change and deactivation revoke automatically inside `save()`**, detected by comparing with the row locked in the same transaction (`SELECT … FOR UPDATE`). Rejected: relying on callers (management commands, future endpoints) to remember. Cost: one extra indexed SELECT per *update* of a user (rare: no `last_login` write, no per-request saves). Reactivation does not bump (tokens died at deactivation). Bypasses: `QuerySet.update()`/`bulk_update()` skip `save()`; no Phase 2 code uses them on `User` and P2-11 adds a test that the commands go through `save()`.
- **Role changes (group membership)** are M2M, not `save()`: the `m2m_changed` hook that bumps the epoch is part of P2-11.
- **Saving a user whose row no longer exists raises `DoesNotExist`.** Django's default would re-insert it with its old epoch and password, un-revoking it.
- **`requires_mfa` is computed from group names and `MFA_REQUIRED_ROLES`.** The spec's `must_enroll_mfa` (requires MFA and has no confirmed device) needs `MfaDevice`; P2-07 adds it on top of this property.
- **Superusers.** Django's `is_superuser` makes `has_perm` return True for everything. Phase 2 users are never created as superusers (P2-13 commands set only groups) and `HasCapability` (P2-05) must evaluate capabilities from role membership **without** honouring `is_superuser`, so the flag cannot bypass RBAC.
- **Password validators** were already on (min 12, common, numeric, similarity). The similarity validator now compares against `email` and `full_name` (there is no username).
- **Tooling:** mypy is now strict on `apps.accounts.*` (migrations excluded); coverage now includes `apps/accounts` (migrations omitted).

## P2-04 Roles, capabilities, RBAC matrix
Sources: Security-Architecture §3 and §9, Backend-Design §4.2, API-Specification operations. Where they are silent or disagree the **safer** reading was chosen.
- **Capability = custom permission on `accounts.User`** (`Meta.permissions`, built from the registry in `roles.py`), granted to Groups by `sync_roles`. Migration `0003` is a metadata-only change (no SQL). Names are `resource.action`; `_own` means "rows in the caller's scope via `for_user()`" (ownership for Campaign Manager, assignment for Sales in Phase 3), `_all` means every row.
- **Added beyond the prompt's minimum list:** `campaigns.update_status` (the contract has `PATCH /campaigns/{id}` to pause/resume/complete; Campaign Manager in scope, Admin all).
- **Contradiction: transcripts and recordings.** Backend-Design §4.2 says both need an *additional* permission; the prompt lists `recordings.listen` and `transcripts.view` separately. Safer reading: **no role holds either by default**; they are granted per user and every access is audited (Security-Architecture §9). Product must confirm whether Admin should hold them by default (OQ2-04).
- **`contacts.suppress` for Campaign Manager (own scope).** Security-Architecture gives suppression *management* to Admin only, but an opt-out request must never wait for an Admin, and suppressing can only reduce calling. `suppression.manage` (view the list, lift entries, cross-campaign) stays Admin-only. Every suppression write is audited (Phase 3 wiring).
- **Sales / Follow-up:** `contacts.view_own` and `final_output.view` only. The spec says "read-only contact views and Final Output"; the scope is undefined, so access is limited to what `for_user()` assigns (Phase 3 decides the assignment model; until then Sales sees nothing). No `attempts.view_*`, so the direct call-attempt endpoints are denied; attempt history nested in the contact view is a Phase 3 serializer decision (OQ2-05).
- **`users.manage` and `api_clients.manage` are held by no role.** There is no REST for them in Phase 2 (management commands, actor `system:cli:<user>`). If an endpoint is added later the matrix test forces a deliberate, reviewed edit.
- **System** has an empty capability set and cannot log in; service accounts are database roles (P2-17) and internal code paths.
- **`client_grantable` registry flag:** only read-only cross-scope capabilities (`campaigns.view_all`, `contacts.view_all`, `attempts.view_all`, `analytics.view_all`, `final_output.view`). `_own` capabilities make no sense for a key with no owner; `*.write`, `recordings.listen`, `transcripts.view`, `audit.view`, `suppression.manage`, imports and status changes are never grantable. P2-12 enforces the flag when scoping a key. Rejected: also allowing `contacts.import` for a CRM (needs a campaign-ownership decision, Phase 3).
- **`sync_roles` makes the registry the source of truth:** it removes *any* permission from a role that the matrix does not grant (including other apps' permissions added by hand) and fails closed (`RuntimeError`) if a registry permission row is missing. It does not touch per-user grants or groups outside the four roles. It runs in one transaction. Concurrent first-ever runs could race on `Group` creation (unique name → one fails and can be re-run); acceptable for a deploy-time command.
- **Logic lives in `accounts/services.py`** (not in the command) so tests and later code can call it; this file is an addition to the layout (also used by P2-11).
- **Audit event for changes is wired in P2-06** (the `audit` app does not exist yet); P2-04 stays `PARTIAL` until then.
- **Generated doc:** `RBAC-MATRIX.md` comes from `python -m scripts.gen_rbac_matrix`; a unit test compares it with the committed file. The truth-table test holds a hand-written copy of the expectations on purpose, so changing the matrix means editing two places in review.

## P2-05 Permission classes and object-level scoping
- **`HasCapability(*names)`** is a cached class factory (`permission_classes = [HasCapability("campaigns.create")]`); several names mean *any of* (a list endpoint accepts `campaigns.view_own` or `campaigns.view_all`, so an API client holding only `_all` can call it). Unknown names or no names raise `ValueError` at import time, so a typo cannot ship as a silently-dead permission.
- **A principal is anything with `is_authenticated` and `has_capability(name)`**: `User` now, `ApiClientPrincipal` in P2-12 (that is how API-key scopes reach the same class; the layout's `ApiClientScope` is realised there). Anything else, a non-`True` answer, or any unexpected exception denies and logs (capability names and view name only). `APIException`s raised by a principal are re-raised so 401/429 still work.
- **`User.capabilities()` ignores `is_superuser`** (decision noted in P2-03) and returns nothing for inactive or unsaved users. It reads group permissions plus per-user grants restricted to registry names, so permissions of other apps (e.g. `add_group` on a role) never become capabilities. One query per request, cached on the instance; `refresh_from_db()` clears it. Role/permission changes made *during* a request are not seen until refresh; tokens issued before a role change die through the epoch (P2-11), so this is not a revocation gap.
- **Scoping contract:** `ScopedQuerySet.for_user(user)`: no principal -> nothing; holder of the model's `view_all_capability` -> everything; otherwise `scope_to_user` (abstract; raises `NotImplementedError`, never "return everything"). `ScopedViewMixin` (a `GenericAPIView` subclass; put it *before* the DRF generic view) makes `get_queryset()` go through `for_user` and raises `ImproperlyConfigured` if the queryset is not scoped. Out-of-scope rows yield **404**, byte-identical to a random UUID (tested), so existence cannot be probed. 403 is reserved for "you may never do this".
- **`ObjectScoped`** is a backstop for views that fetch objects another way: it raises `NotFound` (not 403) for objects outside `for_user`.
- **Lint limits (stated, not hidden):** the lint detects scoped views through a class-level `queryset` attribute and the model lint through the default manager. A view that builds its queryset only in `get_queryset()` without the mixin is caught by review, not by the test. `ScopedViewMixin` does not stop a subclass overriding `get_queryset` without calling `super()`.
- **Per-method capabilities** are not supported by one `HasCapability` (DRF applies the same classes to every method); views that need different capabilities per method are split into separate views (as the test app does) or override `get_permissions`.
- **Test-only app `tests.testapp`:** installed only by `config.settings.test` (asserted for dev/staging/prod). It ships a real migration because an unmigrated app cannot hold a foreign key to the migrated `accounts.User`.
- **Default-deny test (Phase 1 file, extended):** every URL-conf view must contain a `CapabilityPermission` or be in `REVIEWED_EXCEPTIONS` (name -> written justification, length-checked). Authenticated-only views (`IsAuthenticated`) are now violations. The three auth views are added to the exceptions in P2-09 with their justification.

## P2-06 audit app (append-only)
- **Three independent layers, each tested alone** (a mutation of one fails only that layer's tests):
  1. *Model*: `save()` on an existing row, `delete()`, and queryset `update`/`bulk_update`/`delete`/`_raw_delete`/upsert-style `bulk_create` raise `AuditImmutableError`; the model has only a `view` permission (no add/change/delete) and no admin.
  2. *Database*: migration `0002` installs `BEFORE UPDATE OR DELETE` (row) and `BEFORE TRUNCATE` (statement) triggers that raise `restrict_violation`. They are `ENABLE ALWAYS`, so a session setting `session_replication_role = replica` (the usual way to skip triggers) does not bypass them (checked in `pg_trigger`: `tgenabled = 'A'`). Reversible: reverse drops the triggers and function.
  3. *Privilege*: the application role gets INSERT and SELECT only (`deploy/sql/roles.sql`, P2-17). Until then layer 3 is not implemented or tested.
- **Residual risk (accepted, stated):** the table owner or a superuser can still `DROP TRIGGER` (the tests prove it is the trigger that blocks, by dropping it inside a rolled-back transaction). The mitigation is layer 3: the application and worker roles are neither owner nor superuser, and migrations run as a separate role. Tamper-evidence beyond that (hash chaining, WORM export) is OQ2-08.
- **Consequence for test and ops tooling:** Django's `flush` (`TRUNCATE` of every table) is refused, so no test may use `transaction=True`/`TransactionTestCase`, and `manage.py flush` cannot be used on a database that has audit rows. P2-03's migration test was converted to run inside the ordinary rolled-back test transaction (PostgreSQL DDL is transactional); the Phase 1 suite had no other transactional tests (grep).
- **`occurred_at` is `db_default=Now()`** (database statement time, not caller-supplied; `record()` has no such parameter). A test freezes the application clock and shows the stored time is the database's.
- **No foreign keys.** `actor_id` is a plain UUID plus a `actor_label` (e.g. the email at the time), so audit rows survive deletion of users, API clients and objects, and cascades can never touch them.
- **`record()` fails closed:** unknown action or outcome raises `AuditError` (typos cannot create un-queryable events); it **must run inside `transaction.atomic()`** (`ATOMIC_REQUESTS` is off, so this is explicit) so an audit failure rolls the change back. `audited(...)` is the context manager that opens the transaction, runs the change, then writes the event; tested: refused audit write -> change rolled back; database error on the audit insert -> change rolled back; failed change -> no success event. A *failure* event is written separately, in its own transaction, after the failed one rolled back.
- **Actions** live in `apps/audit/actions.py` (`ACTIONS` is derived from the constants). Added to the prompt's list: `auth.mfa.enrollment_started`, `auth.logout_all`. Later phases add theirs there (retry policy, agent config, suppression, recording/transcript access: Security-Architecture §9).
- **Redaction** reuses the Phase 1 log redaction and adds auth names (`otp`, `code`, `totp`, `seed`, `secret_encrypted`, `sessionid`, `csrftoken`, `provisioning_uri`, `x-api-key`, auth cookie names, `key`, `key_hash`). Over-redaction is accepted: a metadata field literally named `code` or `key` is masked, so callers use `error_code`/`name`. Payloads over 16 KiB (before, after, metadata each) are replaced by `{"_truncated": true, "_original_bytes": n}`. Control characters are stripped from labels and the user agent (log-injection hygiene); the user agent is cut at 256 characters.
- **Request context:** request id comes from the Phase 1 log context. Client IP and user agent come from `apps/audit/context.py` (`request_info`), which a middleware binds in P2-10 once the trusted-proxy resolver exists; until then CLI and request events carry no IP. This is a deliberate dependency order, not an omission.
- **Actors:** `Actor.user/api_client/system/anonymous`, plus `Actor.cli()` = `system:cli:<os-user>` (falls back to `unknown` when the OS has no passwd entry, e.g. some containers).
- **Indexes (4):** `occurred_at`; `(actor_id, occurred_at)`; `(object_type, object_id, occurred_at)`; `(action, occurred_at)`: the four ways auditors query (when, who, what object, what kind). Write cost is acceptable at the expected volume. **Expected volume:** auth events plus configuration writes and recording/transcript accesses: order of 10^4 rows/day for a small team, roughly 1 KB each, i.e. a few hundred MB per year. Revisit partitioning by month if the table passes ~50 M rows (OQ2-08).
- **No retention or deletion code in the app.** Retention is an operational process run by a privileged role outside the application (it must drop or detach the trigger deliberately); documented in OPEN-QUESTIONS.
- **Closes the P2-04 gap:** `sync_roles()` writes one `rbac.sync` event, in the same transaction, only when something changed (actor `system:cli:<os-user>` from the command, `sync_roles` when called from code); an audit failure rolls the sync back (tested).

## Phase 1 test fix found during P2-06 (separate commit)
`tests/core/test_logging.py::test_regex_performance_no_catastrophic_backtracking` asserted a 2 s **wall-clock** bound per hostile input. It takes about 0.1 s per input when idle but failed intermittently (about 3 of 14 full runs) when the machine was busy, and was reproduced deterministically-enough under 4 busy loops. It now measures **CPU time** (`time.process_time`), which a busy machine does not inflate, with the same 2 s bound. Detection power is unchanged: a classic catastrophic pattern (`^(a+)+$` on 26 `a`s plus `!`) burns 2.4 s of CPU, i.e. still exceeds the bound. Other wall-clock tests (`tests/core/test_health.py` timeout assertion `< 1.5 s`, the Celery worker start-up wait) did not fail under the same load but are load-sensitive in principle; noted in OPEN-QUESTIONS (OQ2-11).

## P2-07 MFA (TOTP) with encrypted seeds
- **Own TOTP service on `pyotp`, not `django-otp`:** `django-otp` stores the TOTP key in plaintext in the database, so a DB copy would hand an attacker every second factor. Seeds here exist only as `FieldCipher` ciphertext (AES-GCM, key rotation supported). `pyotp` only does the HOTP/TOTP arithmetic; it is checked against the RFC 6238 SHA-1 vectors.
- **Ciphertext is bound to its row, not just its field.** The prompt specifies AAD `accounts_mfadevice.secret`; the context used is `accounts_mfadevice.secret|<device uuid>` (a strict extension). Without the device id, an attacker with database *write* access could copy the ciphertext of a seed they know onto a victim's row and then pass MFA as the victim. With it, the copy fails to decrypt and verification fails closed (tested, and removed-protection mutation fails the test).
- **Plaintext seed lifetime:** generated with `pyotp.random_base32()` (160 bits, OS CSPRNG), returned once inside `Enrollment` (`repr` hides secret and URI), never stored, logged or audited (log-capture and audit tests). Re-sealing on key rotation happens on the next successful verification.
- **Verification:** ASCII `[0-9]{6}` only (so Unicode digits, whitespace and newlines are rejected); +/- 1 step; **all window steps are always evaluated** and compared with `hmac.compare_digest`, so timing does not reveal which step matched. The device row is locked (`SELECT ... FOR UPDATE`) so concurrent attempts cannot both pass the replay check.
- **Replay protection:** `last_used_step` is the highest accepted step; a code for a step at or below it is refused. Consequence (accepted): a code from the *next* step used early (clock drift) makes the current-step code unusable until the following step. A failed attempt never advances the marker. The enrolment code itself cannot be replayed at login.
- **One active and one pending device per user is a database guarantee** (two partial unique indexes), not just application logic. Starting a new enrolment disables the previous pending device. Enrolling while a device is active is refused (`AlreadyEnrolled`): the only way back is `reset_mfa` (management command in P2-13), which disables all devices, bumps `auth_epoch` and audits (`auth.mfa.reset`, actor `system:cli:<os-user>`).
- **Confirming enrolment bumps `auth_epoch`** (prompt requirement): every session issued before MFA was active dies, and so does the enrolment credential.
- **Failures are audited with a reason** (`invalid`, `replay`, `malformed`, `no_device`, `seed_unreadable`) in their own transaction so they survive the failed attempt; the guess itself is never recorded. Reasons are for operators only: the HTTP layer (P2-09) must return one uniform error. Counting failures toward lockout is wired in P2-10.
- **Restricted enrolment credential** (users whose roles require MFA but who have no device):
  - A *signed token* (`django.core.signing`, own salt `accounts.mfa-enrollment`, keyed from `JWT_SIGNING_KEY`), not a JWT: SimpleJWT cannot parse it and it cannot be parsed as one (both directions tested). Lifetime `MFA_ENROLLMENT_TOKEN_LIFETIME_SECONDS` (600). Embeds the user's `auth_epoch`; valid only while the user is active **and** `must_enroll_mfa` is still true (two independent kill switches after confirmation).
  - **Transport: `Authorization: MfaEnroll <token>` header, delivered in the login response body**, not a cookie. It is not an ambient credential, so it needs no CSRF protection, lives for minutes, and can only enrol an authenticator. This deliberately differs from the session tokens (cookies only) and is a spec addition (DOC-PATCHES).
  - `EnrollmentTokenAuthentication` is listed only on the two enrolment endpoints (P2-09); `IsEnrollmentCredential` lets only that credential through them. `request.auth` is an `EnrollmentCredential` marked `restricted`, and **`HasCapability` refuses any restricted credential**, so even a view that wrongly accepts the authenticator cannot grant the user's role capabilities (tested over HTTP).
  - All token failures raise one uniform error (`401`, `WWW-Authenticate: MfaEnroll`, identical body for tampered, expired, revoked and garbage tokens).
- **`must_enroll_mfa`** is computed (`requires_mfa and not has_active_mfa_device`), never stored.
- **Not in Phase 2:** SMS, email OTP, recovery codes, multiple devices (OQ2-12).
